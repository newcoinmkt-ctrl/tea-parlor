# 棋牌室 AI 开发规则

## 1. AI 每次开工前必须确认

- 本次是产品文档、规则、前端、后端、Bot、钱包、风控、部署还是测试任务。
- 是否涉及真实资金、数字货币、提现、用户隐私或后台权限。
- 是否会修改 `.env`、密钥、钱包私钥或数据库迁移。
- 是否会改变游戏规则或结算公式。

## 2. 资料优先级

1. 用户最新明确要求。
2. `AGENTS.md`。
3. `docs/03-架构实施/棋牌室游戏开发说明.md`。
4. `docs/02-规则资料/JJ斗地主规则与玩法说明.md`。
5. `docs/03-架构实施/TeaParlor-x-斗地主游戏厅-桥接说明.md`。
6. 历史产品 docx。

涉及 GitHub 现成游戏时，额外读取：

7. `docs/04-AI开发规则/GitHub现成游戏获取设置.md`。
8. `skills/github-game-importer/SKILL.md`。

如果资料互相冲突，先停下来标注冲突，不要擅自合并成一个不可验证的承诺。

## 3. 开发原则

- 先实现可验证的最小闭环，再扩展玩法和运营功能。
- 斗地主规则引擎放在 `packages/doudizhu-engine`，保持纯函数/纯状态机边界。
- 游戏引擎不直接访问钱包、数据库和链。
- Bot 不承载高速牌桌 UI，牌桌必须在 H5。
- 所有资产相关功能必须账本化、幂等化、可审计。
- 德州扑克、麻将优先用成熟规则库或高覆盖测试，不手写低可信核心算法。
- 从 GitHub 获取的游戏项目必须先隔离评估，不能直接合入正式源码。

## 4. 前端规则

- 先做实际可用大厅，不做纯营销落地页。
- 移动端优先，兼容桌面。
- 视觉参考 QQ 斗地主棋牌室，但使用自有素材。
- 牌桌控件必须适合单手操作。
- 关键按钮固定：叫分/不叫、出牌、不出、提示、托管、退出。
- 文本不得遮挡牌面、按钮和玩家状态。

## 5. 安全与合规规则

- 涉及登录、钱包、提现、后台权限时，必须调用安全审查思路并输出风险清单。
- 不要默认允许美国、中国大陆等敏感地区真实货币玩法。
- 真实充值提现上线前必须有 KYC/AML、地区限制、限额、人工审核、异常冻结和链上对账。
- 不要把影子积分描述成可提现资产。

## 6. 测试规则

斗地主至少覆盖：

- 所有基础牌型解析。
- 炸弹和火箭压制。
- 顺子/连对/飞机不能含 2 和王。
- 叫分流程：不叫、1/2/3、3 分截断、无人叫分。
- 地主拿底牌。
- 春天/反春。
- 输赢以小。
- 幂等结算。

H5 至少覆盖：

- 移动端大厅。
- 移动端牌桌。
- 三人座位。
- 叫分、出牌、结算。
- 断线重连视角。

当前 monorepo 每次修改斗地主规则、演示或基础入口后至少运行：

```bash
cd /Users/newcoin/Desktop/棋牌室
npm run audit:local
npm run demo
```

## 7. AI 提示词模板

开发新功能时可使用：

```text
请先读取 AGENTS.md、docs/03-架构实施/棋牌室游戏开发说明.md，以及与本任务相关的规则文档。
本次目标是：[写清楚目标]。
约束：
1. 不接真实资金，只用影子积分。
2. 游戏引擎不能直接改余额。
3. 斗地主规则以 JJ 经典规则文档为准。
4. UI 参照 QQ 斗地主棋牌室风格，但不用受保护素材。
请完成代码、测试和验证，并说明哪些能力已验证、哪些仍是待办。
```

审查资产/安全时可使用：

```text
请对当前登录、钱包、结算、提现、后台权限做威胁建模。
请区分：已实现风险、上线前必须补齐、后续增强。
不要给出真实资金上线结论，除非合规/KYC/AML/地区限制/对账/审计都已经覆盖。
```
