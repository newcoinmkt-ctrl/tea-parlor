# 一、JJ 游戏厅是什么（详细描述）

## 1.1 一句话

**JJ 斗地主**是竞技世界旗下的**专业棋牌在线竞技平台**：以斗地主为核心，叠加麻将、象棋、掼蛋等，强调**公平赛制、丰富赛事、多端入口、大厅式运营**，而不是单一「三人对一局」的小游戏。

官方定位关键词：**专业棋牌 · 竞技比赛 · 玩法多样 · 免费参赛赢奖 · 公平无作弊**。

## 1.2 产品形态：不是一张桌，而是「厅」

用户打开 JJ 后，进入的是**游戏大厅（Lobby）**，而不是直接进一桌牌。大厅承担：

| 模块 | 作用 |
|------|------|
| **游戏入口矩阵** | 经典斗 / 欢乐 / 癞子 / 闪电 / 二人 / 四人 / 连炸；以及麻将、象棋、掼蛋、跑得快等 |
| **场次分级** | 新手场、普通场、高手场、土豪场等（底分 / 携带分门槛不同） |
| **匹配与开房** | 快速匹配、好友房、指定规则房 |
| **赛事中心** | 锦标赛、回馈赛、排位赛、冠军杯等；有报名、赛程、排名、奖金/奖品 |
| **资产与商城** | 金币/积分、门票、道具、装扮、记牌器等 |
| **社交与荣誉** | 战绩、段位、称号、历史牌局 |
| **活动运营** | 签到、任务、活动页、下载导流多端 |

**「游戏厅」= 大厅导流 + 规则引擎 + 房间服务 + 资产结算 + 赛事运营 + 客户端表现。**

## 1.3 用户一天在 JJ 里会经历什么

```
启动 App / 网页
    ↓
登录账号（JJ 账号体系）
    ↓
大厅：选玩法（如经典斗地主）→ 选场次（底分/入场门槛）
    ↓
匹配 3 人成桌 或 进入好友房
    ↓
发牌 → 叫分/抢地主 → 出牌 → 结算
    ↓
继续下一局 / 换场 / 去锦标赛报名 / 商城装扮
```

核心爽点：

1. **秒匹配**：不用自己凑人。  
2. **规则清晰、节奏可控**：超时托管、提示出牌。  
3. **有攀升感**：场次、段位、赛事奖金。  
4. **公平感知**：专业赛制、防作弊宣传。  
5. **可玩很久**：玩法矩阵 + 活动不断档。

## 1.4 经典斗地主在「厅」里的位置

大厅里点进「斗地主」后，通常还有**二级选择**：

- **玩法**：经典叫分 / 欢乐叫地主 / 癞子 / 不洗牌 / 闪电…  
- **场次**：不同底分、基数、携带上下限、封顶倍数  
- **模式**：自由场 vs 锦标赛（门票报名、瑞士轮/淘汰等）

一局经典玩法骨架（JJ 公开规则）：

- 3 人，54 张，每人 17 张 + 3 底牌  
- 叫 1/2/3 分定地主，底牌公开  
- 地主先出，逆时针跟牌  
- 炸弹/火箭/春天等影响倍数  
- 结算：`地主分 = 2 × 胜负 × 基数 × 底分 × 倍数`；农民无「2」系数  
- 常有 **「输赢以小」**（按携带分封顶输赢）

## 1.5 JJ 游戏厅的「系统分层」（从产品反推架构）

| 层 | JJ 侧能力 | 说明 |
|----|-----------|------|
| **展示层** | 多端客户端 | 大厅 UI、动画、装扮 |
| **接入层** | 账号、大厅协议 | 登录、列表、匹配请求 |
| **大厅服务** | Lobby / Match | 场次配置、匹配队列、房间分配 |
| **游戏服** | 牌桌状态机 | 发牌、叫分、出牌、回放 |
| **资产服** | 金币/门票 | 带入、结算、输赢以小 |
| **赛事服** | 锦标赛 | 报名、赛程、排名 |
| **运营后台** | 配置与风控 | 开关场次、活动、封禁 |
| **数据** | 战绩与审计 | 牌谱、举报、对账 |

## 1.6 JJ 式「厅」的关键体验特征（做 TG 版要对齐的点）

1. **配置驱动**：场次、底分、倍数、玩法靠后台配置，不靠发版。  
2. **房间生命周期完整**：匹配 → 开局 → 托管 → 结算 → 下一局/解散。  
3. **失败可恢复**：断线重连、托管代打。  
4. **公平叙事**：随机发牌、可回放（JJ 偏竞技宣传）。  
5. **运营闭环**：任务、活动、赛、商城持续拉日活。  
6. **多玩法容器**：斗地主只是大厅里的一个「游戏插件」。

## 1.7 和「单一 Bot 小游戏」的区别

| | 单一 TG 小游戏 | JJ 式游戏厅 |
|--|----------------|-------------|
| 入口 | 一个命令开一局 | 大厅 → 选玩法/场次 |
| 规模 | 熟人房为主 | 匹配池 + 赛事 |
| 资产 | 无或极简 | 完整账本与场次门槛 |
| 运营 | 几乎无 | 活动/赛/商城 |
| 扩展 | 难加新游戏 | 插件化玩法矩阵 |

**你要做的 TG Bot 游戏厅，应对标「厅」，而不是只做一个 `/play` 开桌。**

# 二、TG Bot 游戏厅与 JJ 的差异与取舍

## 2.1 Telegram 能提供什么

| 能力 | 用途 |
|------|------|
| **Bot API** | 命令、按钮、消息、群通知 |
| **Mini App (WebApp)** | 完整 H5 大厅 + 牌桌 UI（强烈推荐） |
| **登录** | Telegram Login / `initData` 校验，零密码 |
| **拉人** | 深链、分享卡片、群邀请 |
| **支付（可选）** | Stars / 第三方 / 链上（视合规） |

## 2.2 TG 做不到或很难 1:1 复制 JJ 的点

- 没有原生「精美 3D 大厅」App 壳，**体验靠 Mini App H5**。  
- Bot 消息流不适合高速出牌 UI → **牌桌必须在 Mini App / 独立 Web**。  
- 群内 Bot 能力受限 → **公会桌需群主授权**，不能乱 @ 全群。  
- 赛制、装扮、TV 端等可后置。

## 2.3 推荐产品形态（务实）

```
Telegram 用户
    │
    ├─ Bot：报名、匹配、通知、分享、查分、客服入口
    │
    └─ Mini App（主战场）
            ├─ 大厅：玩法列表、场次、资产、任务
            └─ 牌桌：实时出牌 UI（WebSocket）
```

**原则：Bot 做触达与轻交互；Mini App 做大厅 + 牌桌。**

# 四、推荐技术架构

## 4.1 逻辑架构

```
                    ┌─────────────────┐
                    │  Telegram Cloud │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼                              ▼
        ┌──────────┐                  ┌─────────────┐
        │ Bot API  │                  │  Mini App   │
        │ 服务     │                  │  (React)    │
        └────┬─────┘                  └──────┬──────┘
             │                               │
             └───────────┬───────────────────┘
                         ▼
                  ┌──────────────┐
                  │ API Gateway  │  鉴权 initData / Session
                  └──────┬───────┘
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
   ┌──────────┐   ┌────────────┐  ┌─────────────┐
   │ Lobby /  │   │ Game       │  │ Wallet /    │
   │ Match    │   │ Servers    │  │ Ledger      │
   └────┬─────┘   │ (斗地主)   │  └──────┬──────┘
        │         └─────┬──────┘         │
        ▼               ▼                ▼
   PostgreSQL        Redis          PostgreSQL
   (用户/配置)     (房间/匹配)       (账本真相源)
```

## 4.2 服务边界（必守）

| 服务 | 做什么 | 不做什么 |
|------|--------|----------|
| **Bot** | 命令、通知、拉起 Mini App | 不算牌、不改余额 |
| **Gateway** | 鉴权、路由 | 不直连写账本库 |
| **Lobby** | 场次列表、匹配、开房 | 不跑出牌状态机 |
| **Game Server** | 牌局状态机、广播 | **不直连 SQL 账本** |
| **Wallet** | 锁分、结算入账、流水 | 不懂具体牌型 |

游戏与资产之间用 **gRPC / MQ 意图**：`BuyInLock` / `Settlement` / `ForceTearDown`。


# 五、分阶段实施步骤（路线图）

> 原则：**先厅的骨架 + 一桌能玩，再赛事与多玩法。**  
> 对齐「1A 影子积分 → 真资产」思路，避免一上来做支付。

## Phase 0 · 工程底座（约 1 周）

**目标**：能部署、能登录、有空大厅。

| 步骤 | 动作 | 产出 |
|------|------|------|
| 0.1 | 注册 BotFather，拿到 Token | Bot |
| 0.2 | 申请 / 配置 Mini App URL | WebApp 入口 |
| 0.3 | monorepo + CI + docker-compose | 本地一键起 |
| 0.4 | PostgreSQL / Redis | 基础设施 |
| 0.5 | Gateway：校验 `initData`，发 Session | 登录通 |

**操作要点：**

1. [@BotFather](https://t.me/BotFather) → `/newbot`  
2. `/setdomain` 绑定 Mini App 域名（HTTPS）  
3. 环境变量：`BOT_TOKEN`、`WEBAPP_URL`、`JWT_SECRET`、`DATABASE_URL`、`REDIS_URL`

**验收：** 点 Bot 菜单打开 Mini App，能显示「你好，@username」。

---

## Phase 1 · 大厅 + 影子积分（约 2–3 周）

**目标**：有 JJ 式「选场」感觉，但用**测试币/积分**，不上真钱。

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1.1 | 用户表、余额表、场次配置表 | Schema |
| 1.2 | 大厅 API：玩法列表、场次列表 | Lobby API |
| 1.3 | Mini App 大厅 UI | 可点选场次 |
| 1.4 | 新用户赠送初始积分 | 冷启动 |
| 1.5 | Bot：`/start`、`/balance`、`/play` 拉起 WebApp | 触达 |

**场次配置示例（后台可改）：**

| 场次 ID | 名称 | 底分 | 入场最低携带 | 基数 |
|---------|------|------|--------------|------|
| newbie | 新手场 | 1 | 100 | 10 |
| normal | 普通场 | 2 | 500 | 20 |
| pro | 高手场 | 5 | 2000 | 50 |

**验收：** 用户能看到类似 JJ 的「玩法 → 场次」两级入口，能看到自己的积分。

---

## Phase 2 · 匹配 + 经典斗地主可玩（约 3–5 周）

**目标**：**3 人匹配成桌，完整打完一局并结算积分。**

| 步骤 | 动作 | 产出 |
|------|------|------|
| 2.1 | 匹配队列（Redis）按场次分池 | Match |
| 2.2 | 创建 Room，分配 game-server | 房间 |
| 2.3 | 斗地主状态机：发牌/叫分/出牌/结束 | Engine |
| 2.4 | 牌桌 Mini App + WebSocket | 实时 UI |
| 2.5 | 带入锁分 + 结算写账本 | Wallet |
| 2.6 | 超时托管、断线重连 | 体验 |
| 2.7 | 牌谱简单回放/日志 | 审计 |

**状态机（实现清单）：**

```
WAITING → DEAL → BIDDING → PLAYING → SETTLE → WAITING/CLOSED
```

**验收：**

- 3 个 TG 号匹配进同一桌  
- 叫分、出牌、炸弹倍数正确  
- 结算后三人积分变化正确、有流水  
- 杀进程重连能恢复手牌视角

# 六、操作指南（从 0 到可玩）

## 6.1 准备清单

- [ ] Telegram 账号  
- [ ] 一台有公网 HTTPS 的服务器（或 Cloudflare Tunnel）  
- [ ] 域名（Mini App 必须 HTTPS）  
- [ ] Docker / Node 20+  
- [ ] PostgreSQL、Redis  

## 6.2 创建 Bot（操作）

1. 打开 Telegram，搜索 **@BotFather**  
2. 发送 `/newbot`，按提示设置名称与 username  
3. 保存 **HTTP API Token**（机密）  
4. `/setcommands` 示例：

```
start - 打开游戏厅
play - 快速开始
balance - 我的积分
help - 帮助
```

5. `/newapp` 或 Bot 设置里配置 **Menu Button → Web App**，URL 填 `https://你的域名/`  
6. `/setdomain` 绑定 Mini App 域名  

## 6.3 本地开发最小闭环

```bash
# 1. 克隆/初始化 monorepo
pnpm install

# 2. 配置环境变量
cp .env.example .env
# BOT_TOKEN=...
# WEBAPP_URL=https://xxx.ngrok.io
# DATABASE_URL=postgres://...
# REDIS_URL=redis://...

# 3. 迁移数据库
pnpm db:migrate

# 4. 启动
pnpm dev   # gateway + bot + lobby + game + web
```

**本地公网：** 使用 `ngrok http 5173` 或 `cloudflared tunnel`，把 HTTPS 地址配进 BotFather。

## 6.4 Mini App 登录校验（必须）

1. 前端：`window.Telegram.WebApp.initData`  
2. 后端：用 Bot Token 按官方算法校验 HMAC  
3. 通过后签发自己的 Session JWT  
4. 之后 API / WS 只认 Session，不信客户端 user_id  

## 6.5 开一局的标准操作流（联调）

| 步骤 | 谁 | 操作 |
|------|----|------|
| 1 | 用户 A | Bot `/start` → 打开大厅 → 选「新手场」→ 开始匹配 |
| 2 | 用户 B/C | 同样匹配同一场次 |
| 3 | Lobby | 凑满 3 人 → 创建 room → 通知 Game Server |
| 4 | Wallet | 三人 `BuyInLock` 锁定入场分 |
| 5 | Game | 发牌、叫分、出牌… |
| 6 | Game | `SubmitSettlement` |
| 7 | Wallet | 写流水、解锁、改余额 |
| 8 | Bot/App | 推送结算卡片；可点「再来一局」 |

## 6.6 日常运营操作

| 场景 | 操作 |
|------|------|
| 改新手场底分 | 后台改 `rooms` 配置，热更新缓存 |
| 维护 | 开维护开关，匹配拒绝，Bot 发公告 |
| 用户投诉少算分 | 查 `hand_id` 牌谱 + `t_ledger` 流水 |
| 刷子多开 | 规则引擎拉黑，限制匹配 |
| 活动 | 配置「今日 10 局 +50 分」任务 |

# 七、斗地主规则引擎要点

（与 JJ 经典场对齐的实现清单）

## 7.1 必须实现

1. 洗牌发牌 17+17+17+3  
2. 叫分状态机  
3. 牌型识别与合法性  
4. 比较与压制（含炸弹/火箭）  
5. 出牌轮转与「不出」  
6. 胜负与倍数  
7. 结算事件（供 Wallet）  

## 7.2 牌型

单、对、三、三带一/二、顺子、连对、飞机、飞机带翅、四带二、炸弹、火箭。

## 7.3 结算（可配置）

```
地主分 = 2 * result * base * bid * multiplier
农民分 =     result * base * bid * multiplier
```

可选：春天、输赢以小、封顶倍数。

## 7.4 单测建议

对引擎做 **纯函数单测**（不启动服务）：

- 每种牌型合法性  
- 边界：最小顺子、连对含 2 非法  
- 炸弹压飞机等  
- 叫分截断 3 分

# 九、合规、风控与安全

## 9.1 合规（务必评估）

- **纯娱乐积分、不可兑法币**：风险相对低，仍需隐私合规。  
- **真金 / 可提现**：多数地区属博彩或强监管，需持牌或停止该地区。  
- Telegram 支付与 Promotions 政策需单独阅读。  
- 提供青少年与地区限制开关。

## 9.2 安全最低标准

| 项 | 要求 |
|----|------|
| 登录 | 校验 initData，防伪造 user_id |
| 资产 | 仅 Wallet 写账本；Game 只发意图 |
| 带入 | Active Lock，防对局中提现/转走 |
| 密钥 | Bot Token 仅服务端 |
| 日志 | 牌局事件可追溯 |

## 9.3 风控最低标准（积分场也建议）

- 同 TG 号限制  
- 同 IP 匹配频率  
- 异常胜率抽查  
- 举报入口

# 结语

做一个 **TG 上的 JJ 式斗地主游戏厅**，本质不是「写个出牌 Bot」，而是：

> **大厅运营容器 + 可配置场次 + 实时牌桌引擎 + 账本结算 + TG 触达。**

- **JJ 游戏厅**提供的是「玩法矩阵 + 场次 + 赛事 + 公平竞技」的完整心智。  
- **TG 实现**应用 **Bot 拉新触达 + Mini App 承载大厅与牌桌**。  
- **实施**上坚持：先影子积分跑通经典三人局，再运营化，再谈赛事与真资产。
